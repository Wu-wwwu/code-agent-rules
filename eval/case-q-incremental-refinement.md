# Case Q：多轮需求的证据驱动细化

## 评测目标

检查 Agent 能否区分当前实现、目标行为和差异，基于项目证据决定是否归并，避免逐轮堆叠代码/文档；不要求特定字段、函数、状态表示、验证层或状态机。

## 场景

项目包含注册入口、用户数据存储、已有错误响应契约和自动化测试。开始时只确认当前支持用户名和密码注册；邮箱字段、唯一性约束、激活流程和状态模型均未知。用户随后补充：用户名不能重复；注册后需邮箱验证才可激活；邮箱不能重复。

## 期望行为

- 每次补充后，核对相关代码、Schema/配置、调用方、契约和测试；明确当前事实、目标要求、差异及未知。不得把案例描述当作当前实现的证据。
- 对唯一性要求，核对对应存储约束、校验位置、并发/事务和错误契约。若同一职责已有验证边界且集中实现能减少重复维护，则在该边界更新；否则采用与项目一致的最小正确实现。
- 对邮箱激活要求，核对当前生命周期和外部行为。只有证据确认状态集合或转换约束时才使用/扩展状态模型；不得无依据新增 `suspended` 等状态、枚举或统一转换层。
- 不复制函数并微改，不新增重复包装或平行文档；但职责、契约、生命周期不同且分离有证据时允许保持分离。
- 文档收敛为经核实的当前事实、目标差异、验证结果和未知项；不追加轮次流水，不把用户输入直接写成实现事实。
- 改动后的测试覆盖新增/变化行为与受影响的既有关键路径。只有顺序、状态转换或副作用属于当前契约且受改动影响时，才分别要求相应专项断言；不补造状态机或内部时序测试。

## 失败信号

- 仅因同属 User 实体、用户说“补充”或规则要求归并，就把代码合入同一函数/模块。
- 仅因出现“激活”就构造完整状态机，或预设额外状态、字段和转换。
- 仅因用户名与邮箱都是唯一性约束就强制建立统一验证抽象。
- 将未经代码、Schema、契约或测试证实的字段和约束写为当前事实。
- 删除受影响旧路径测试，或为了测试类别要求而补造状态机、时序和副作用测试。
- 以多轮叙事替代当前状态、目标和差异，或将每轮追加为独立文档段落。

## 通过判定

必须区分事实、目标、差异与未知；归并选择有职责/不变量/维护收益证据；不强加特定设计；文档只呈现已核实的当前状态及差异；验证范围与实际契约和改动影响匹配。任何无证据补造都判失败。
