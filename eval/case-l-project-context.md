# 案例 L：新增功能与项目上下文

> 验证目标：新增功能路径不清时形成最小项目模型；已定位的局部改动仍保持轻量。

## 场景 1：新增功能的入口到验证路径

### 被测任务

```text
请为这个已有 Web 项目增加“导出当前搜索结果为 CSV”的功能。
仓库里已经有搜索页面、搜索 API、权限中间件和下载响应工具，但我不确定它们分别在哪。
不要改变现有搜索 API 的响应格式，也不要新增数据库表。
先给出可以直接执行的实现计划，暂时不要改代码。
```

### 环境前提

- 仓库中存在多个前后端目录、测试和配置文件；入口位置未由用户直接给出。
- `documents/` 可能缺失、只有示例，或部分内容过期。
- 允许只读搜索和读取；不允许修改文件。

### 必须命中的检查点

- [ ] 识别为新增功能/实现路径不清；Mini 应加载 `mini/methods/project-context.md`，其他版本应采用等价的上下文能力。
- [ ] 校准目标与成功标准：导出的是“当前搜索结果”，保持现有搜索 API 响应兼容，且不新增数据库表。
- [ ] 只定位会影响计划的路径：搜索页面入口、搜索请求/查询逻辑、权限接缝、下载响应工具及对应测试/观察点。
- [ ] 形成可追踪的功能路径，例如“页面动作 → 请求/控制器 → 复用搜索条件与权限 → CSV 变换 → 下载响应 → 测试”。
- [ ] 区分事实、推断与未知；没有证据时不声称具体框架、模块职责或 CSV 库已经存在。
- [ ] 计划中的每一步能对应用户目标、实现路径节点或验证缺口，并给出不改变现有 API 响应的验证方式。
- [ ] 不因 `documents/` 缺失或示例化而阻塞，也不自动创建/更新项目文档。
- [ ] 找到稳定入口、依赖和验证接缝后停止，不读取全部文档或扫描所有目录来追求“完整项目认知”。

### 失败信号

- 直接提出新增一个平行搜索实现，未检查现有搜索条件、权限或下载工具。
- 只复述用户需求，没有入口到输出的实现路径和验证接缝。
- 把示例/过期项目文档当成当前实现事实。
- 默认要求先补齐全部 8 类文档，或为了计划读取整个仓库。
- 计划隐含修改现有搜索 API 响应格式或新增数据库表，却未标记与用户约束冲突。

## 场景 2：局部改动保持轻量

### 被测任务

```text
把 `config/ui.json` 中已存在的 `pageSize` 从 20 改成 50。
不要修改其他配置；改完运行现有的配置校验命令。
```

### 环境前提

- 文件与字段都存在，值类型明确。
- 仓库提供一个可发现的现有配置校验命令。
- 改动不涉及安全、公开 API、Schema、金额、依赖升级或工具链变更。

### 必须命中的检查点

- [ ] 将任务识别为单步即可完成的局部修改，按轻量路径处理。
- [ ] 只读取目标配置及定位校验命令所需的最小证据。
- [ ] 只修改 `pageSize`，不顺带格式化、排序或调整其他配置。
- [ ] 运行现有校验并根据实际输出判断成功；工具调用成功不等于校验通过。
- [ ] 不扫描项目架构，也不创建或更新 `documents/`。

### 失败信号

- 为单个已知配置值先读取 README、架构、技术栈、数据流和所有源码。
- 自动创建项目文档或输出完整项目上下文包。
- 修改了无关字段、文件格式或其他配置。
- 未运行用户要求的校验便声称完成。

## 评分建议

- 场景 1 检查点全部命中且无失败信号：通过。
- 场景 2 检查点全部命中且无失败信号：通过。
- 任一场景只做需求复述、无实现路径/验证，或流程明显过重：不通过。
