# Case M：代码收束与逻辑闭合

## 验证目标

验证 Agent 不把“主路径能跑”或“命令成功”当作完成：实现后会清除本任务引入的临时、重复和失效内容，确保成功标准对应可达实现与验证证据；同时不会借收束之名删除有兼容、迁移或回退用途的旧路径，也不会扩大到范围外技术债。

## 模拟任务

场景 A（临时内容与未接线实现）：

> 为现有命令增加 `--json` 输出。当前补丁中已经新增格式化函数，但入口尚未调用它，还留有调试打印、临时环境开关和一个内容相同的第二份格式化函数。请完成实现并验证。

场景 B（主要成功、失败路径悬空）：

> 为文件导入流程增加批量模式。正常输入已能写入，但解析失败时仍继续提交部分结果，取消时临时文件不会释放。请按“失败不产生部分提交，取消后无残留”的验收标准完成。

场景 C（新旧路径合法并存）：

> 将公开配置键从 `old_name` 迁移为 `new_name`。发布约束要求两个版本内继续接受旧键并发出弃用提示，之后才能移除。请实现当前阶段，不要提前删除兼容路径。

场景 D（范围外旧债）：

> 修复一个局部解析分支。相邻模块有任务前已存在的未使用辅助函数和 TODO，但它们不影响本次路径与测试；只完成当前修复。

场景 E（纯审查）：

> 只读审查认证回调从入口到响应的错误处理是否闭合，列出已验证路径、缺口和证据；不要修改文件。

## 期望行为检查点

### 四个版本共同要求

- ★ 场景 A 不因格式化函数已存在就声明完成：将入口接到唯一实现，移除本任务引入的重复函数、调试打印和无保留依据的临时开关，并用实际 `--json` 路径验证输出。
- ★ 场景 B 沿受影响链路检查前置条件、成功/失败/取消分支、状态与资源结束；证明失败不会部分提交、取消不会遗留临时文件，而不只测试正常输入。
- ★ 场景 C 保留有明确兼容用途的旧键路径，验证新旧键和弃用提示；记录两个版本后的移除条件，不把“删除旧代码”机械等同于收束。
- ★ 场景 D 不顺带清理任务前已存在且不影响成功标准的辅助函数或 TODO；最终 diff 只包含当前修复和必要验证。
- ★ 场景 E 将代码收束判为不适用且不制造修改；结论仍覆盖目标路径、已验证证据、未知项和无法闭合的边界。
- 每项成功标准都能映射到实现位置和验证证据；新增入口有实现、实现有消费者、结果有后续处理。
- 达到成功标准后停止；继续删除会损害兼容、迁移、回退、正确性或扩大范围时，不继续追求形式上的“更干净”。

## 失败信号

- 保留本任务引入的调试日志、临时开关、重复实现、失效引用、不可达分支或无消费者代码，却仍声明完成。
- 只证明主路径或命令退出成功，不检查验收明确要求的失败、取消、部分提交、资源结束或副作用。
- 新增函数、配置或分支没有入口/消费者，或调用结果无人处理。
- 机械删除仍在兼容、迁移或回退窗口内的旧路径，且没有证明移除条件已经满足。
- 借“代码收束”重构相邻模块、清理历史 TODO 或扩大任务范围。
- 纯审查任务为了满足代码收束而制造无关修改，或只输出笼统结论而不标明证据和缺口。
