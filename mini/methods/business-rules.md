# 业务规则分析

> **触发条件**：涉及金额计算、货币转换、支付/退款/结算、财务对账/报表，或状态/权限/角色相关业务决策。
> **轻量路径**：任务不改变金额、状态、权限或角色语义（如纯展示、日志、格式调整）时按 agent.md 处理；规则已被有效证据确认且未过期时复用证据，但仍验证实现是否符合规则。

## 定位规则

1. 先按 `methods/project-documents.md` 检查目标项目的 `documents/business-rules.md`，不得默认文件存在或把示例内容当项目事实
2. 文件有效且命中时，引用对应规则条目及其证据来源
3. 文件缺失、占位或未命中时，从用户确认、业务资料、代码判断、Schema 和测试中定位规则；缺失文件不等于没有业务规则
4. 没有可验证依据时，不得推测目标行为

## 边界确认

金额、币种、支付、结算、状态、权限和角色等词只触发分析，不直接决定风险级别或确认深度。不同项目先形成最小风险画像：

1. **代码路径**：从用户可观察入口追踪到规则判断、权限/校验边界、状态或数据写入、外部调用、输出和测试接缝；检查并发、幂等、重试及调用方。
2. **数据流**：识别权威来源、输入/存储/传输/输出表示、精度和单位、约束变换、持久化与共享范围、派生数据、对账或恢复方式。
3. **业务流程**：定位前后步骤、状态转换、参与角色、自动/人工节点、时间窗口、外部副作用、失败补偿和用户可见结果。
4. **关键资源**：依据目标项目的代码、配置、Schema、测试、有效文档或用户资料，识别错误计算、错误授权、重复执行、泄露或不可用会造成显著损害的资源；不得只按通用行业经验预设，也不得因未命中常见关键词而忽略项目特有资源。

输出最小风险画像：受影响资源、代码/数据/流程路径、失败后果、影响范围、可检测性、可恢复性和证据。风险取决于实际后果、影响范围、可检测性与可恢复性，而不是关键词数量；信息不足且可能改变方案或正确性时只补相应证据。

识别与风险画像直接相关的时间、状态、精度、单位、角色等边界条件，选取最多 3 个关键场景。仅在规则缺失或冲突，或存在会改变关键资源、业务结果或安全边界的真实语义选择时，请求用户明确确认；已有直接、适用且未过期的规则证据时，不为确认而重复确认，但仍验证实现与影响。

需要确认时，展示依据、风险画像和关键场景；用户拒绝则停止对应语义选择并提出替代方案，要求调整则更新规则与画像后重新确认，未回复或回复含糊时保持暂停。仅确认总体目标不等于确认具体业务语义。若画像命中数据删除、安全放宽、不兼容契约或不可逆外部副作用等信号，同时加载 `methods/destructive-analysis.md`，不得用业务确认替代其风险门禁。

## 实现方式

使用伪代码或流程图明确前置条件、全部判断分支和返回结果。实现时在关键判断处标注对应业务规则编号。

## 决策框架

当需要在多个方案中选择时：

| 步骤 | 内容 |
|------|------|
| 1. 识别冲突 | 明确冲突点（技术、业务、资源） |
| 2. 方案对比 | ≥2 方案，各 ≥2 优缺点 |
| 3. 推荐方案 | 给出推荐理由 |
| 4. 标注影响范围 | 涉及的模块、数据、测试 |

## 决策记录

需要长期追溯时，先按 `methods/project-documents.md` 检查或按需初始化目标项目的 `documents/decision-log.md`。记录包含：编号、日期、标题、状态、冲突点、背景、方案对比、最终选择、影响范围、证据、重提条件。

新建决策条件（三者同时满足）：难以撤销、无上下文会惊讶、存在真实权衡。任一不满足则不建档。

## 决策优先级

1. 数据安全/正确性 > 性能
2. 可维护性 > 代码简洁性
3. 显式 > 隐式
4. 内部一致性 > 外部最佳实践
