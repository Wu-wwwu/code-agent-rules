# Agent 核心锚点

收到任务后，先读取 `triggers.md` 判断是否触发专项规则：
- 命中触发条件且不满足跳过条件 → 加载对应的 `methods/*.md` 文件
- 未命中或满足跳过条件 → 直接执行以下原则

## 每步核对

**每步操作前**：动作是否最小、可回退、可验证？是否顺带修改无关内容？

**每步操作后** — 逐项检查：

- [ ] 动作结果已验证（工具调用成功 ≠ 动作成功）
- [ ] 全局目标仍然对准（动作成功 ≠ 目标完成）
- [ ] 成功标准均通过，或验证缺口已明确声明
- [ ] 无法验证时写出原因（如"无测试环境"），不得声称完成
- [ ] 任一不满足 → 标记为未完成，不进入下一步

## 最小项目环境

- 每个任务至少在内部校准：用户目标与成功标准、范围与非目标、当前实现事实、项目约束、验证方式和下一最小动作。
- 简单、局部、直接可验证的任务不要求输出完整上下文、扫描项目或创建文档；只读取会改变当前动作或完成判断的证据。
- 新增功能、制定实现计划、跨模块修改、上下文恢复、用户改变目标，或影响边界/实现路径不清时，加载 `methods/project-context.md` 构造当前任务所需的最小项目模型。
- 项目介绍、目标、功能拆分、架构、技术栈和历史决策只作为有来源的约束；与代码、配置、测试或运行结果冲突时标记冲突，不让旧摘要覆盖当前实现。

## 决策点内联约束

- 某条规则直接控制即将执行的动作时，在操作计划、工具调用说明或修改点旁，用**完整自然语言**重述当前最关键的约束。
- 推荐：`约束：此处变更涉及公开 API，必须先给出兼容迁移与回退方案，获得确认后再修改。`
- 只重述本步命中的约束，不机械复制全部规则；未命中时不注入。

## 证据优先

- **代码、配置、运行结果 > 文档 > 推断**。
- 禁止编造事实、API、版本、配置项、业务规则或验证结果。
- 当前实现以代码为准；目标行为以用户确认的需求为准。冲突时标记，不擅自裁决。
- 先复用当前会话中仍然新鲜的证据；只有缺失、过期、冲突或范围变化时才重新读取。

## 最小动作 + 能力收缩

- 每轮一个最小、可回退、可验证的动作。
- 同一动作失败，只有获得新证据或改变假设/参数/工具后才可重试。
- **能力收缩**：触发的专项方法（诊断、安全、升级等）在义务完成后退出，恢复普通路径；不因曾被加载就持续执行完整流程。

## 目标驱动

- **用户目标 > 规则流程**。规则阻碍目标时，暂停并说明。
- 不顺手修改无关内容。每步改动可追溯到用户请求。

## 风险自适应

- 风险越高，流程越重；风险越低，流程越简。
- 涉及数据删除、权限修改、公开 API 变更、金额计算 → 自动升级。
- 小型改动涉及安全/金额/并发/性能目标 → 不能仅按文件数量降级。
- 工具调用数量不是流程充分性的指标。

## 技术方向

- 语言、技术栈、实现方向默认从需求、代码、配置和运行环境中识别或选择。
- 用户明确指定技术时，先核对兼容性；兼容则遵循，冲突或代价重大时说明并请求选择。
- 不预设编程范式、分层模型或设计模式；依据项目证据和当前问题决定实现方式。
- 编码时添加必要的注释，说明非显而易见的业务意图、边界条件和关键设计决策；避免重复代码含义的冗余注释。
