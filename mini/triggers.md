# 触发规则

## 触发跳过条件

匹配触发条件，但**满足以下任一条件时不加载方法**，直接用 anchors 原则处理：

| 跳过条件 | 说明 | 示例 |
|---------|------|------|
| 已有新鲜上下文 | 当前会话已加载该方法，证据未过期 | 上一轮刚加载过 destructive-analysis，本轮不重复 |
| 单步即可完成 | ≤3 步可完成，无多方案选择或风险升级 | 改一个已知配置值，不涉及安全或 Schema 变更 |
| 纯信息任务 | 只查阅/解释/比较，不产生修改 | 询问"这个 breaking change 是什么"而非执行升级 |
| 用户已给出完整决策 | 用户提供了明确的判断依据和边界 | 用户说"这次升级用 SET_NULL，已和 DBA 确认" |

**用法**：匹配触发条件 → 先判跳过条件 → 跳过则按 anchors 原则处理 → 不跳过则加载方法走完整流程。

## 触发规则详解

### T1：数据/权限破坏性操作
**触发**：删除表/列/行、修改用户/角色权限、覆盖配置文件、调用有副作用的外部 API。
**行为**：暂停，输出影响分析（受影响元素、类型、影响说明）和回退方案，等待用户确认。

### T2：公开 API/Schema 变更
**触发**：修改公开 API 请求/响应格式、数据库 Schema、共享数据契约。
**行为**：执行扩展-收缩迁移（扩展→分批迁移→收缩），输出迁移计划和回退方案，等待用户确认。

### T3：金额/金融业务逻辑
**触发**：金额计算、货币转换、支付/退款/结算、财务对账/报表。
**行为**：先检查目标项目的 `documents/business-rules.md` 是否存在且有效；不可用时从用户说明、业务资料、代码、Schema 和测试定位规则，不得把缺失解释为没有规则。没有可验证依据时不得推测。识别边界条件，选取 ≤3 个与改动直接相关的关键场景请求确认。

### T4：历史决策回查
**触发**：任务涉及历史技术决策、需确认当前做法是否符合历史约定。
**行为**：先检查目标项目的 `documents/decision-log.md` 和可选 `documents/glossary.md`；有效时检索，缺失/示例时声明历史覆盖不足并从代码、提交历史和当前上下文补充，不得推断“没有历史决策”。命中冲突→输出冲突提示并暂停；命中 rejected→输出重提条件；不冲突→标注关系继续。

### T5：依赖 major 升级
**触发**：升级依赖到新 major、上游弃用到期、上游移除。
**行为**：检查上游 changelog/breaking change→评估声明文件/锁文件/生成物/CI-CD/容器/部署环境→对于需要逐步迁移的变更，遵循 `methods/destructive-analysis.md` 中的扩展-收缩模式；涉及数据安全决策（如 CASCADE vs SET_NULL）时逐处或分类与用户确认→输出迁移计划和回退方案。

### T6：工具链/生成物变化
**触发**：修改代码生成器/格式化器/编译器版本、修改构建工具配置、修改 CI/CD 流水线。
**行为**：确定作用域层级（项目本地 > 用户级 > 全局）→只修改任务授权且实际生效的最小层级→同时检查声明文件、锁文件、生成物、CI/CD、容器和部署环境。

### T7：多 Agent 协作
**触发**：任务可拆分为独立子任务、需并行调查多个模块、需不同专业域审查。
**行为**：定义任务包契约（目标、范围、完成标准、返回格式）→子 Agent 默认只读或返回补丁，共享工作区采用单写者模型→只有能证明独立工作区并明确所有权、合并顺序时才并行写入→主 Agent 串行整合并复核关键事实。

### T8：技术选型
**触发**：现有项目的语言/框架/存储不明确、新项目需决定技术栈、技术方向可能改变系统边界。
**行为**：用户明确指定→核对兼容性，兼容则遵循，冲突则展示证据和选项；用户未指定→从项目证据识别，边界内自主选型；选择改变高影响边界时输出方案并请求确认。

### T9：复杂 Bug 诊断
**触发**：Bug 涉及竞态/时序/非确定性/跨模块交互，或无法稳定复现，或用户未提供完整复现步骤。
**行为**：先判快速路径：目标有直接依据+修改局限于既有接缝+不改公开 API/Schema/业务规则→跳过诊断流程。否则：建立反馈回路（失败测试/CLI 快照/请求回放）→复现并最小化→提出 3-5 个可证伪假设→插桩验证（一探针对应一预测）→修复并回归→清理调试代码。

### T10：性能/容量验证
**触发**：性能、容量、延迟、吞吐或资源消耗是目标或方案依据。
**行为**：记录可重复基线（环境、当前耗时、执行计划）→用相同工作负载比较→没有可比测量时不得声称优化完成→输出测量结果和对比数据。

### T11：抽象判断与设计方式中立
**触发**：涉及新增抽象层、引入设计模式、提取公共代码、新增分层/架构组件、重构代码结构。
**行为**：加载 `methods/neutral-design.md`→先观察现有代码风格和组织方式→优先在既有结构内完成最小修改→满足"相同知识+相同使用方+相同变化原因+≥2 处生产使用"时才可抽象→不预设范式或设计模式，依据项目证据决定。

### T12：数据实体与表示变换
**触发**：需要从代码标识、类型、Schema、数据库表、序列化格式中识别或归并数据实体，推导实体关系，或输出数据构件的创建与变换过程。
**行为**：加载 `methods/data-entity-analysis.md`→将名称视为检索线索而非现实对象证明→只按代码、约束、映射、调用、测试或用户证据保持关联→用中性实体标识按“来源/创建→校验→查询/补全→变换→持久化/传递→输出”记录；不得引入相关现实领域知识和概念。

### T13：项目上下文与实现路径
**触发**：新增功能、制定或修订实现计划、任务跨越多个模块、上下文恢复、用户改变目标，或当前改动与项目目标/功能边界/入口到验证路径的关系不清。
**行为**：加载 `methods/project-context.md`→先复用当前会话和有效项目文档→只补充会影响方案、范围、风险或验证的代码与配置证据→形成目标、非目标、项目关联、实现路径、约束、未知和验证方式组成的最小任务上下文包→在关键动作旁重述命中的项目约束。简单局部任务、纯信息任务或已有新鲜完整上下文时按跳过条件保持轻量。
