# 最小实现门禁

## 适用时机

实现新功能、选择实现方式、增加依赖/抽象，或新需求涉及已有代码时，按本门禁检查。局部直接修改只检查会影响该修改的项目，不输出清单或扩展调查。

## 实现选择顺序

实施前依次判断，命中后仍须满足后续安全、正确性和验证要求：

1. **目标必要性**：实现项必须服务于明确需求、成功标准或已验证的业务约束。未要求且非必要的功能、选项和扩展不实现；目标有歧义且会改变行为时先澄清。
2. **现有实现**：检索相关调用方、组件、工具、依赖和项目约定。可满足目标时优先复用或修改现有实现，不另建平行路径。
3. **平台能力**：现有实现不适用时，使用项目支持的标准库或平台能力；不得重复实现等价功能。
4. **现有依赖**：平台能力不适用时，检查已安装依赖并优先复用。新增依赖前说明必要能力、替代方案、维护/安全/许可/运行影响；不得仅为少量便利函数引入依赖。依赖规模、行数或人气不能单独作为准入或否决依据。
5. **最小正确实现**：以上均不适用时，采用满足全部成功标准的最小可读实现。不得为缩短 diff 删除必要分支、错误处理、安全校验、兼容、迁移、回退或测试。

## 合并与删除

- 新需求若细化已有实体、流程或约束，先按 `./incremental-refinement.md` 归并到当前实现；只有目标或变化原因独立时才新增实现。
- 新实现替代旧实现时，确认调用方、消费者、兼容和回退影响。无当前消费者且无留存义务时删除失效实现；需要并存时记录依据、责任边界和可观察的移除条件。不得以“可能以后用”作为保留理由，也不得清理任务范围外旧代码。
- 已知且当前可接受的限制仅在影响维护或验收时记录，并写清限制、适用范围和可观察的复核条件；不创建无消费者的通用技术债清单。

## 完成检查

确认每项新增功能、抽象、依赖、配置和分支都对应目标或必要约束，已有路径已被复用或其不适用有证据，替代关系已处理，且验证覆盖目标及受影响的既有行为。未通过时先收敛实现；遇到安全、授权、兼容或回退冲突时遵循相应专项门禁。
