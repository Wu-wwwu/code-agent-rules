# 疑难 Bug 诊断

**总原则**：无反馈回路，不假设。

## 阶段一：建立反馈回路
优先失败测试、HTTP 脚本、CLI 快照、请求回放、最小 harness、模糊测试、差分回路。记录单次运行耗时并选择足以支持重复试验的最快可用回路；不得为了“秒级”替换掉能复现原始症状的必要环境。断言必须对应原始症状，环境和输入保持可重复。

- 症状只在特定版本区间出现：用版本二分（如 `git bisect`）定位引入点。
- 时序窗口型竞态：用循环触发脚本拉高命中次数。
- 非确定性 Bug：先提高复现率（经验基线 50%，启发式默认值）并记录复现基线。注意区分必现的逻辑交错型竞态与概率性的时序窗口型竞态——前者按确定路径复现，不需要复现率指标。

## 阶段二：复现 + 最小化
确认症状一致，逐项删减输入、状态、时序、依赖和环境条件；当再删除任一剩余条件都会使症状消失或变为不同问题时，得到承重集合。记录无法继续删减的证据，不把“看起来最小”当作结论。

## 阶段三：可证伪假设
每批最多选择 2 个有区分力的可证伪假设，每个对应可执行验证和预期信号；依据结果更新下一批，不限制整个诊断的假设总数。格式："若 X 是原因，则改变 Y 应使 Bug 消失 / 改变 Z 加重"。

## 阶段四：插桩
每探针对应一预测，一次改一变量。调试器优先，所有日志前缀 `[DEBUG-xxxx]`。

## 阶段五：修复 + 回归
最小复现 → 回归测试 → 看红 → 修复 → 看绿 → 重跑原始回路。测试打在正确接缝上。

## 阶段六：清理
- 原始场景不复现
- 回归测试通过
- 调试日志删除
- 临时 harness 清理
- 架构性发现只有影响未来修改且不可从当前实现直接推导时才保留为相关方案的依据；独立建档按 `business-analysis.md`「新建决策条件」，不因发现问题就追加日志。
