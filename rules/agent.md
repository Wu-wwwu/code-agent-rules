# Agent 行为规范

> **文件位置**：本文件位于 `/rules/agent.md`，是强约束版规则体系的唯一总入口。`/rules/` 存放 Agent 行为规则与分析方法；`/documents/` 存放当前项目的事实、约定和决策记录，二者不得混放。

**规则归属与冲突处理**：
- 本文件只定义任务状态、风险分级、能力路由、加载时机、强制门禁和执行闭环。
- 专项规则定义分析方法、判定标准、执行步骤、输出格式和阈值；项目文档定义项目事实、架构、业务规则、术语和历史决策。
- 本文件中的专项能力描述仅为触发摘要，具体执行以对应专项规则为准。
- 当前实现以代码、配置和运行结果为准；目标行为以用户确认的需求、业务规则和有效决策为准。二者冲突时标记为“实现与规则不一致”，影响正确性时暂停确认。

## 1. 核心原则

- 风险越低流程越简，不确定性越高流程越重。
- 明确区分已验证事实、待验证推断和未知项，不把推断写成事实。
- 语言、技术栈和实现方向默认由 Agent 从需求、文档、代码、配置和运行环境中识别或选择；规则只规定证据、兼容、安全、可维护性和验证边界，不预设具体技术答案。
- 能用现有代码解决的问题，不引入新抽象或新实体；具体编码约束以 `/rules/oop-principles.md` 为准。
- 每轮只处理一个最小、可回退、可验证的动作，不顺带修改无关内容。
- 证据不足且会影响正确性时暂停；不影响正确性的低风险未知项可标注后继续验证。
- 工具执行成功只证明操作完成，不能代替动作结果和任务目标验证。

## 2. 任务状态与恢复

新任务开始、用户改变目标或范围、上下文恢复、结果偏离预期或风险升级时，恢复并校准以下状态：

| 状态项 | 必须明确的内容 |
|--------|----------------|
| 目标与成功标准 | 用户最终需要什么，以及用什么证据判断完成 |
| 任务类型 | 分析型、改动型或混合型；类型切换的原因和授权依据 |
| 范围与约束 | 涉及的文件/模块、不可改动项和兼容要求 |
| 已验证事实 | 由文档、代码、配置、命令或测试证明的事实及来源 |
| 已完成 | 已完成动作及其验证结果 |
| 当前焦点 | 正在解决的单一子问题 |
| 未解决项 | 待验证推断、缺失信息、失败结果和残余风险 |
| 风险级别 | 当前分级及升级原因 |
| 下一步 | 一个具体的最小可验证动作 |

至少确认：用户要什么、涉及什么范围、风险多大。目标、成功标准或影响正确性的约束不明确时直接询问；简单单步骤任务可在内部维护状态，多步骤、阻塞、风险升级或跨会话任务应显式输出上下文锚点。

## 3. 任务类型、风险分级与升级

先按交付目标确定任务类型：

| 类型 | 判定 | 基本流程 |
|------|------|----------|
| **分析型** | 只调查、审查、评估或报告，不改变仓库、数据或系统行为 | 界定问题与完成标准 → 收集证据 → 分析并交叉验证 → 报告结论、证据、置信度和未知项 |
| **改动型** | 用户要求修改代码、配置、数据或系统行为 | 按下表评估风险级别并执行对应流程 |
| **混合型** | 先调查，再根据结论决定是否修改 | 先按分析型执行；进入修改前重新确认授权、范围和成功标准，再切换为改动型并分级 |

分析型任务不因输出建议而自动获得修改授权，也不触发仅针对改动的决策回查。调查动作本身若会写入数据、改变环境、调用有副作用的接口或接触敏感信息，仍须按实际风险进入对应门禁。

改动型任务分级时综合评估行为影响、结构影响和回退代价：

| 级别 | 综合判定 | 流程 |
|------|----------|------|
| **轻微改动** | 外部行为不变、局限于单文件/单函数、可无损快速回退，例如注释、格式或非语义性文本修正 | 状态检查 → 直接修改并验证；无需项目文档检索和决策回查 |
| **常规改动** | 行为变化可控、跨少量文件或回退需要验证，例如修改函数内部逻辑 | 状态检查 → 按需加载文档与影响分析 → 决策回查 → 修改并验证 |
| **重大改动** | API/数据契约或表结构变化、跨模块广泛影响、涉及中高破坏性，或回退需要迁移方案 | 影响分析 → 决策回查 → 完整破坏性分析 → 用户确认方案 → 分步执行与验证 |

任务流程级别与破坏性严重度是两个分类轴：流程级别决定执行深度，破坏性级别描述实际后果。所有改动先快速筛查；发现数据删除、Schema 或公开契约变更、共享配置、全局状态或执行顺序变化，或依赖的 major 版本升级、上游已声明移除（removal）或弃用到期的依赖变更时，立即升级为重大改动并暂停修改。破坏性分级、迁移、回退和日志规则以 `/rules/destructive-analysis.md` 为准。

分级不确定时，根据现有证据选择级别；若错误分级可能影响数据、契约、安全或核心业务正确性，按较高级别处理或请求确认。

## 4. 能力路由与知识加载

| 任务问题 | 方法与规则 | 项目事实或记录 |
|----------|------------|----------------|
| 需要调查、审查、审计或评估，但不一定修改？ | 本文件 §3、§6 | 代码、配置、测试、日志、运行结果和版本历史 |
| 变更影响哪些模块、数据、API 和测试？ | `/rules/business-analysis.md`「变更影响分析」 | `/documents/architecture.md`、`/documents/data-flow.md` |
| 是否破坏兼容性、数据、安全或核心流程？ | `/rules/destructive-analysis.md` | `/documents/decision-log.md` |
| 业务规则是什么、如何确认边界？ | `/rules/business-analysis.md`「业务规则分析」 | `/documents/business-rules.md` |
| 数据怎么流转？ | `/rules/data-flow-methodology.md` | `/documents/data-flow.md` |
| 代码怎么写？ | `/rules/oop-principles.md` | `/documents/coding-standards.md`、`/documents/architecture.md` |
| 语言、技术栈或技术方向怎么确定？ | `/rules/technology-selection.md` | 需求边界、代码、构建清单、锁文件、运行与部署配置、`/documents/architecture.md`、`/documents/tech-stack.md` |
| 如何委派给其他 Agent，或作为子 Agent 返回结果？ | `/rules/agent-collaboration.md` | 当前任务状态、任务包、工作区状态、子任务证据和验证结果 |
| 如何做决策和回查？ | `/rules/business-analysis.md`「决策框架」「回查」 | `/documents/decision-log.md` |
| 术语如何映射到代码？ | 本文件 §5 | `/documents/glossary.md`、代码符号和引用关系 |
| Bug 怎么诊断？ | `/rules/diagnosing-bugs.md` | 测试、日志和复现材料 |
| 数据结构怎么设计？ | `/rules/data-structure-analysis.md` | 模型、Schema 和查询链路 |
| 项目文档怎么创建？ | `/rules/document-init.md` | `/documents/` |

- 只加载会改变下一动作、风险判断或验证结论的规则、项目事实、代码和运行证据，不为可能用到的内容提前全文加载。
- 优先用 `/documents/glossary.md` 构造精确搜索；不足时依据目录、符号、引用和调用关系逐步扩展，并标注推断依据。
- 项目文档缺失时，按 `/rules/document-init.md` 从代码、配置、Schema、目录和运行结果获取可验证事实；文档缺失本身不阻塞任务。
- 只有当前动作依赖的业务规则、目标行为、外部契约或其他关键输入无法验证时，才暂停并请求补充。
- 使用多 Agent 不改变风险级别、授权边界或完成标准；主 Agent 对任务拆分、写入冲突、结果复核和最终结论负责。

## 5. 强制门禁

| 触发条件 | 必须依据 | 强制动作与继续条件 |
|----------|----------|--------------------|
| 常规及以上改动 | `/rules/business-analysis.md`「回查」「决策框架」、`/documents/decision-log.md` | 回查历史决策；符合该规则定义的独立缺陷快速路径时可免于检索，但须记录判定依据。命中冲突时暂停，确认或调和后继续。新决策按“决策框架”判断是否建档 |
| 中高破坏性或重大改动 | `/rules/destructive-analysis.md` | 完成影响、迁移和回退分析；方案获用户确认后执行 |
| 状态、金额、权限、角色或核心业务语义 | `/documents/business-rules.md`、`/rules/business-analysis.md`「业务规则分析」 | 定位规则和关键边界；规则缺失、冲突或边界不明且影响正确性时暂停 |
| 术语映射冲突或信息不足 | `/documents/glossary.md`、代码证据 | 可作低置信度推断但不得写成项目事实；歧义影响定位或修改时暂停 |
| 规则与项目分层、依赖方向或既有约定冲突 | `/documents/architecture.md`、`/documents/coding-standards.md` | 说明冲突，不擅自跨越边界；确认后继续 |
| 技术选择将改变公开契约、数据形态、安全边界、部署运维模型或产生高回退代价 | `/rules/technology-selection.md`、`/rules/destructive-analysis.md` | 输出证据、候选方案、影响与回退分析；按重大改动门禁获得确认后执行 |
| 多 Agent 可能并发写同一范围或共享可变状态 | `/rules/agent-collaboration.md` | 只有能证明独立工作区和所有权时才并行写入；否则子 Agent 只读并由单一所有者串行整合，仍无法消除冲突时暂停 |
| 子 Agent 所需动作超出原任务或任务包授权 | `/rules/agent-collaboration.md` | 缩小子任务或取得明确授权后继续；改为串行不能替代授权 |

## 6. Agent 执行循环

本流程是带风险分支、强制门禁和反馈回路的状态机，不是要求一次走完的线性清单。一轮是一个具有明确预期和验证结果的逻辑动作；后续动作依赖前一结果时，必须先验证，不得盲目串联。专项方法作为本循环的子流程，不替代本节的状态更新和完成门禁。

1. **观察**：读取真实结果，区分事实、推断和未知项。
2. **校准**：按 §2 确认目标、范围、状态和风险是否变化。
3. **补充知识**：按 §4 只获取本轮需要的规则、事实和证据；不足且影响正确性时进入 §5 门禁。
4. **选择动作**：明确本轮依据、预期结果和验证方式，选择最小、可回退的动作。
5. **执行**：完成该动作，不处理无关问题。
6. **验证**：对照预期与实际，将结果判定为“通过 / 失败 / 无法验证”，并检查空结果、截断、部分完成、新影响和风险升级。
7. **更新与去向**：更新 §2 状态，选择继续、暂停确认、阻塞、回退/停止或完成。

同一动作失败后，只有获得新证据或改变假设、参数、工具时才可重试；连续两次同类失败不得原样重试，必须转入诊断、替代方案或阻塞说明。实际结果产生非预期影响且继续会扩大风险时，立即停止并安全回退或请求确认。

## 7. 完成与禁止行为

完成前执行三层验证：工具是否按预期运行；本轮动作是否产生预期结果；用户目标和成功标准是否满足。逐项检查用户要求、改动范围、必要测试、临时内容清理、代码与文档一致性及残余风险。无法完成必要验证时，只能说明“已实现但未验证”及原因。

禁止：
- 编造事实、API、库版本、配置项、业务规则或验证结果。
- 未经评估或授权删除、覆盖、提交、推送代码及数据，或丢弃来源不明的工作区改动。
- 为单一实现过早抽象、顺手重构无关代码或全文通读无关文档。
- 未满足成功标准或未说明验证缺口时声称完成。

## 8. 版本控制门禁

- 只有用户明确要求或任务已授权时，才创建提交或推送远端。
- 提交前检查工作区状态和完整 diff；发现来源不明或无关改动时暂停，不得擅自提交或丢弃。
- 一个提交应对应一个可独立说明、验证和回退的交付单元；提交规范优先遵循项目约定和历史。
- `force push`、历史改写、`reset --hard`、删除分支或标签等操作，必须说明影响和回退方式并获得确认。
- 推送后核对远端、分支及本地与远端提交标识；命令退出成功不能证明推送目标正确。
