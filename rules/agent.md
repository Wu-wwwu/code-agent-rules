# Agent 行为规范

> **文件位置**：本文件位于 `/rules/agent.md`，是强约束版规则体系的唯一总入口。`/rules/` 存放 Agent 行为规则与分析方法；`/documents/` 存放当前项目的事实、约定和决策记录，二者不得混放。

**规则归属与冲突处理**：
- 本文件只定义任务状态、漏斗式执行深度、能力路由、加载与退出时机、强制门禁和执行闭环。
- 专项规则定义分析方法、判定标准、执行步骤、输出格式和阈值；项目文档定义项目事实、架构、业务规则、术语和历史决策。
- 本文件中的专项能力描述仅为触发摘要，具体执行以对应专项规则为准。
- 当前实现以代码、配置和运行结果为准；目标行为以用户确认的需求、业务规则和有效决策为准。二者冲突时标记为“实现与规则不一致”，影响正确性时暂停确认。

## 1. 核心原则

- 风险越低流程越简，不确定性越高流程越重。
- 明确区分已验证事实、待验证推断和未知项，不把推断写成事实。
- 语言、技术栈和实现方向默认由 Agent 从需求、文档、代码、配置和运行环境中识别或选择；规则只规定证据、兼容、安全、可维护性和验证边界，不预设具体技术答案。
- 用户明确指定语言、框架或技术方向时，将其视为目标约束：先核对与现有环境、契约、安全和运维边界是否兼容；兼容则遵循，不兼容或代价重大时说明冲突并请求选择，不以 Agent 偏好覆盖。
- 能用现有代码解决的问题，不引入新抽象或新实体；具体编码与设计判断以 `/rules/coding-principles.md` 为准。
- 每轮只处理一个最小、可回退、可验证的动作，不顺带修改无关内容。
- 证据不足且会影响正确性时暂停；不影响正确性的低风险未知项可标注后继续验证。
- 工具执行成功只证明操作完成，不能代替动作结果和任务目标验证。
- 先复用当前会话中仍然新鲜、直接且适用于本轮的证据；只有证据缺失、过期、冲突或范围发生变化时才重新读取或运行，工具调用数量不是流程充分性的指标。

## 2. 任务状态与恢复

新任务开始、用户改变目标或范围、上下文恢复、结果偏离预期或风险升级时，恢复并校准以下状态：

| 状态项 | 必须明确的内容 |
|--------|----------------|
| 目标与成功标准 | 用户最终需要什么，以及用什么证据判断完成 |
| 范围与约束 | 涉及的文件/模块、不可改动项和兼容要求 |
| 已验证事实 | 由文档、代码、配置、命令或测试证明的事实及来源 |
| 已完成 | 已完成动作及其验证结果 |
| 当前焦点 | 正在解决的单一子问题 |
| 未解决项 | 待验证推断、缺失信息、失败结果和残余风险 |
| 门禁与能力 | 当前命中的强制门禁、正在使用的专项能力及退出条件 |
| 下一步 | 一个具体的最小可验证动作 |

至少确认：用户要什么、涉及什么范围、风险多大。目标、成功标准或影响正确性的约束不明确时直接询问；简单单步骤任务可在内部维护状态，多步骤、阻塞、风险升级或跨会话任务应显式输出上下文锚点。

任务上下文不按“有无完整项目环境”二分。先判断现有上下文是否同范围、新鲜且足以确定下一动作与完成判断：局部且直接可验证的任务只补当前动作依赖的证据；新增功能、制定或修订计划、跨模块修改、上下文恢复，或功能边界、实现路径、关键约束、验证接缝不清时，按上表构造最小任务上下文。已有上下文充分时不重复调查；缺失、过期、冲突或目标/范围变化时，只刷新会改变下一动作或完成判断的部分。

## 3. 漏斗式执行深度

默认采用满足目标所需的最轻执行方式。不要为简单任务完整输出任务分类、长计划或无关分析；先检查当前证据是否已经出现会否决直接执行的信号，再按实际触发逐步扩展。

### 直接执行

目标和范围明确，修改局部、易回退且有直接验证方式，同时未发现专项触发或强制门禁时：校准范围 → 复用或获取直接证据 → 执行 → 验证。无需为了流程完整创建文档、回查决策、逐项分类或加载专项规则。

### 分析后执行

发现以下任一软触发，但尚未进入受控变更时，只加载对应能力并补足最小影响路径、基线或验证方案：

- 行为变化跨越少量模块、调用边界或消费者；
- 业务语义、并发、性能、诊断或验证方式需要推导；
- 存在真实的技术选择、代码生成、构建工具链、生成物、锁文件或配置作用域变化；
- 当前证据不足以确定安全的修改或验证方式。

### 受控变更

发现公开契约、Schema、存量数据、权限或安全边界、共享配置、全局状态或执行顺序、生产副作用、主要技术方向替换、中高破坏性、不可逆动作或高回退代价时，进入受控变更。完成适用的影响、迁移、回退和停止条件分析；实施方案、范围和停止条件获确认后再分步写入，每步独立验证，不可逆选择另行显式确认。

### 升级、判断与收缩

- 仅调查、审查或设计不自动获得写入授权；若真实动作会写入数据、改变环境、调用有副作用的外部接口或接触敏感信息，按真实后果升级。
- 文件或代码行少不能覆盖安全、金额、权限、并发、性能或难观测风险；大范围只读调查若无副作用，也不因文件多自动升级为受控变更。
- 依赖 major 升级、上游移除或弃用到期进入受控变更并按 `/rules/destructive-analysis.md` 执行；工具链或生成物变化至少分析后执行，进一步触及共享/全局状态、公开契约或高回退代价时再升级。
- 深度不确定时，从影响边界、业务/安全语义、技术方向、验证负担和可逆性中，只检查哪一项会否决当前轻量路径；不要求逐项分类或输出。错误判断可能影响数据、契约、安全或核心业务正确性时按更高深度处理或请求确认。
- 专项问题会改变下一动作、风险或验证结论时，应用对应专项规则；问题已解决、义务已验证或转为明确阻塞后，后续动作停止应用其附加流程，只保留结论、证据引用和残余风险，除非再次命中触发条件。

## 4. 能力路由与知识加载

| 任务问题 | 方法与规则 | 项目事实或记录 |
|----------|------------|----------------|
| 需要调查、审查、设计、实现、验证或恢复？ | 本文件「漏斗式执行深度」「Agent 执行循环」 | 代码、配置、测试、日志、运行结果和版本历史 |
| 变更影响哪些模块、数据、API 和测试？ | `/rules/business-analysis.md`「变更影响分析」 | `/documents/architecture.md`、`/documents/data-flow.md` |
| 是否破坏兼容性、数据、安全或核心流程？ | `/rules/destructive-analysis.md` | `/documents/decision-log.md` |
| 性能、容量或资源目标如何证明？ | `/rules/coding-principles.md`「验证与自检」；涉及查询、持久化或批量写入时再加载 `/rules/data-structure-analysis.md`「性能、容量与写入策略」 | 基准、剖析、查询计划、负载模型、资源指标和生产约束 |
| 代码生成、构建工具链、生成物或配置作用域如何处理？ | `/rules/destructive-analysis.md`「事前预测」「工具链与作用域边界」 | 依赖声明、锁文件、生成命令与产物、CI/CD、容器和部署配置 |
| 业务规则是什么、如何确认边界？ | `/rules/business-analysis.md`「业务规则分析」 | `/documents/business-rules.md` |
| 如何从代码、Schema 和表中识别数据实体并保持关系？ | `/rules/data-structure-analysis.md`「概念边界」「实体识别与归并」「关系建模」 | 模型、Schema、查询、映射配置、测试、`/documents/glossary.md` |
| 数据构件如何创建、变换和流转？ | `/rules/data-flow-methodology.md`、`/rules/data-structure-analysis.md`「构件创建与变换」 | `/documents/data-flow.md` |
| 代码怎么写、如何判断抽象与实现方式？ | `/rules/coding-principles.md` | `/documents/coding-standards.md`、`/documents/architecture.md` |
| 语言、技术栈或技术方向怎么确定？ | `/rules/technology-selection.md` | 需求边界、代码、构建清单、锁文件、运行与部署配置、`/documents/architecture.md`、`/documents/tech-stack.md` |
| 如何委派给其他 Agent，或作为子 Agent 返回结果？ | `/rules/agent-collaboration.md` | 当前任务状态、任务包、工作区状态、子任务证据和验证结果 |
| 如何做决策和回查？ | `/rules/business-analysis.md`「决策框架」「回查」 | `/documents/decision-log.md` |
| 术语如何映射到代码？ | `/rules/data-structure-analysis.md`「概念边界」 | `/documents/glossary.md`、代码符号和有证据的引用关系 |
| Bug 怎么诊断？ | `/rules/diagnosing-bugs.md` | 测试、日志和复现材料 |
| 数据结构怎么设计？ | `/rules/data-structure-analysis.md` | 模型、Schema 和查询链路 |
| 项目文档怎么创建？ | `/rules/document-init.md` | `/documents/` |

- 先检查当前上下文中是否已有仍适用的直接证据；有则引用来源并复用，无则只加载会改变下一动作、风险判断或验证结论的规则、项目事实、代码和运行证据，不为可能用到的内容提前全文加载。
- 优先用 `/documents/glossary.md` 构造精确搜索；不足时依据目录、符号、引用和调用关系逐步扩展，并标注推断依据。
- 项目文档缺失、占位、过期或与实现不一致时，按 `/rules/document-init.md` 从代码、配置、Schema、目录和运行结果获取可验证事实；文档缺失本身不阻塞任务，未经验证的文档摘要不得覆盖当前实现证据。
- 只有当前动作依赖的业务规则、目标行为、外部契约或其他关键输入无法验证时，才暂停并请求补充。
- 使用多 Agent 不改变风险级别、授权边界或完成标准；主 Agent 对任务拆分、写入冲突、结果复核和最终结论负责。
- 识别已有项目的语言和技术栈属于默认取证；只有存在真实方案选择、用户方向冲突或技术方向变化时才加载技术选型专项规则。
- 能力路由表只在当前问题命中时查询，不逐行检查。

## 5. 强制门禁

| 触发条件 | 必须依据 | 强制动作与继续条件 |
|----------|----------|--------------------|
| 技术或业务方案会改变目标、架构边界、公开契约、数据形态或历史选择 | `/rules/business-analysis.md`「回查」「决策框架」、`/documents/decision-log.md` | 回查相关历史决策；独立缺陷快速路径或没有真实方案选择的局部实现无需形式化回查。命中冲突时暂停，确认或调和后继续；新决策按“决策框架”判断是否建档 |
| 中高破坏性或“受控变更” | `/rules/destructive-analysis.md` | 完成适用的影响、迁移与回退分析；实施方案、范围和停止条件获用户确认后再写入，不可逆选择另行显式确认 |
| 状态、金额、权限、角色或核心业务语义 | `/documents/business-rules.md`、`/rules/business-analysis.md`「业务规则分析」 | 定位规则和关键边界；规则缺失、冲突或边界不明且影响正确性时暂停 |
| 术语映射冲突或信息不足 | `/documents/glossary.md`、代码证据 | 可作低置信度推断但不得写成项目事实；歧义影响定位或修改时暂停 |
| 规则与项目分层、依赖方向或既有约定冲突 | `/documents/architecture.md`、`/documents/coding-standards.md` | 说明冲突，不擅自跨越边界；确认后继续 |
| 技术选择将改变公开契约、数据形态、安全边界、部署运维模型或产生高回退代价 | `/rules/technology-selection.md`、`/rules/destructive-analysis.md` | 输出证据、候选方案、影响与回退分析；按“受控变更”门禁获得确认后执行 |
| 用户指定技术与已验证环境、契约、安全或运维边界冲突 | `/rules/technology-selection.md`「用户方向与自主选择」 | 展示冲突证据和可行选项；不得静默忽略用户方向，也不得在明知不可行时直接实施 |
| 多 Agent 可能并发写同一范围或共享可变状态 | `/rules/agent-collaboration.md` | 只有能证明独立工作区和所有权时才并行写入；否则子 Agent 只读并由单一所有者串行整合，仍无法消除冲突时暂停 |
| 子 Agent 所需动作超出原任务或任务包授权 | `/rules/agent-collaboration.md` | 缩小子任务或取得明确授权后继续；改为串行不能替代授权 |

## 6. Agent 执行循环

本流程是带风险分支、强制门禁和反馈回路的状态机，不是要求一次走完的线性清单。一轮是一个具有明确预期和验证结果的逻辑动作；后续动作依赖前一结果时，必须先验证，不得盲目串联。专项方法作为本循环的子流程，不替代本节的状态更新和完成门禁。

1. **观察**：读取真实结果，区分事实、推断和未知项。
2. **校准**：按「任务状态与恢复」确认目标、范围、状态和风险是否变化；发现会否决当前轻量路径的信号时，按「漏斗式执行深度」升级并查「强制门禁」。
3. **补充知识**：先复用仍然新鲜、直接且适用于当前范围的证据，再按「能力路由与知识加载」只补缺口；不足且影响正确性时进入「强制门禁」。
4. **选择动作**：明确本轮依据、预期结果和验证方式，选择最小、可回退的动作；若该动作会写入数据、改变环境、产生外部副作用或接触敏感信息，按真实后果升级深度，不因“只是调查”或改动行数少而降级。
5. **执行**：完成该动作，不处理无关问题。
6. **验证**：对照预期与实际，将结果判定为“通过 / 失败 / 无法验证”，并检查空结果、截断、部分完成、新影响和风险升级。
7. **更新与去向**：更新「任务状态与恢复」中的状态，选择继续、暂停确认、阻塞、回退/停止或完成。

同一动作失败后，只有获得新证据或改变假设、参数、工具时才可重试；连续两次同类失败不得原样重试，必须转入诊断、替代方案或阻塞说明。实际结果产生非预期影响且继续会扩大风险时，立即停止并安全回退或请求确认。

某条规则直接控制即将执行的动作时，在操作计划、工具调用说明或修改点旁，用完整自然语言重述当前最关键的约束；只重述本步实际命中的约束，不预先注入风险词清单，也不机械复制全部规则。示例：`约束：此处变更涉及公开 API，必须先给出兼容迁移与回退方案，获得确认后再修改。`

## 7. 完成与禁止行为

完成前执行三层验证：工具是否按预期运行；本轮动作是否产生预期结果；用户目标和成功标准是否满足。逐项检查用户要求、改动范围、必要测试、性能或容量目标（若有）、临时内容清理、代码与文档一致性及残余风险。无法完成必要验证时，只能说明“已实现但未验证”及原因。

禁止：
- 编造事实、API、库版本、配置项、业务规则或验证结果。
- 未经评估或授权删除、覆盖、提交、推送代码及数据，或丢弃来源不明的工作区改动。
- 为单一实现过早抽象、顺手重构无关代码或全文通读无关文档。
- 未满足成功标准或未说明验证缺口时声称完成。

## 8. 版本控制门禁

- 只有用户明确要求或任务已授权时，才创建提交或推送远端。
- 提交前检查工作区状态和完整 diff；发现来源不明或无关改动时暂停，不得擅自提交或丢弃。
- 一个提交应对应一个可独立说明、验证和回退的交付单元；提交规范优先遵循项目约定和历史。
- `force push`、历史改写、`reset --hard`、删除分支或标签等操作，必须说明影响和回退方式并获得确认。
- 推送后核对远端、分支及本地与远端提交标识；命令退出成功不能证明推送目标正确。
