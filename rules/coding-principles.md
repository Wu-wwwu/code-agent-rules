# 编码与设计准则

> 本规则规定实现阶段的行为边界和判断标准，不预设编程语言、编程范式、分层模型或设计模式。语言、技术栈和技术方向按 `./technology-selection.md` 从项目证据与用户边界中确定。

## 0. 基本准则

### 0.1 编码行为准则

| 原则 | 核心规则 |
|------|---------|
| **依据已确认目标编码** | 不在实现阶段引入未经确认的业务假设；发现新歧义时返回 `./agent.md` 主流程处理 |
| **简洁优先** | 不加要求外的功能；不为一次性代码建抽象；候选同样满足成功标准时，优先新增概念、文件/类型、依赖、配置、状态、分支、调用跳转和回退步骤更少的实现 |
| **精准修改** | 不改相邻代码、注释或格式；不随手改不相关代码；以现有文件编码格式为准；匹配现有风格；每项修改都能追溯到用户目标；不把用户请求、规则文本或过程说明写入代码注释 |
| **目标驱动** | 将抽象目标转化为可观察、可验证的结果；多步骤任务为每一步设置验证点 |

### 0.2 通用设计原则

| 原则 | 触发信号 |
|------|---------|
| **KISS** | 完成后比较新增概念、依赖、状态、分支、调用跳转、测试接缝和回退步骤，采用满足成功标准且负担更小的方式 |
| **YAGNI** | 只为明确需求编码，不推测未来需求 |
| **DRY** | 重复时先判断是“相同知识”还是“碰巧相同的代码”，仅对前者消除重复 |
| **最少知识** | 模块读取未由公开/稳定契约提供的内部状态，或一次行为需跨多处内部对象才能验证时，收拢交互边界 |
| **关注点分离** | 不同变化原因混在一起时，按项目现有结构分离职责 |
| **显式优于隐式** | 隐式状态、依赖、控制流或错误处理影响理解和验证时，改为显式表达 |

### 0.3 职责与表示

- 先依据实际调用、输入输出、数据变化和副作用判断代码职责，不依据文件名、目录名或预设分层判断。
- 数据访问与持久化代码优先使用数据表示分析：字段、键、约束、查询形状、映射、事务、索引、并发和一致性；实现目标是正确、可验证且适配存储语义的存取结构。将“持久化处理”与“内存变换”作为数据流阶段和边界来区分，不自动拆成目录、类或服务。
- 内存变换关注输入/输出表示、字段与约束变化、可变性、生命周期、复制/共享和计算复杂度；持久化处理额外关注存储模型、索引、事务、锁、幂等、提交可见性、恢复和迁移。两者之间的映射必须显式且可验证。
- 业务流程与领域逻辑优先使用模型分析：业务概念、状态转换、生命周期、不变量、规则边界和用户可观察结果；只有跨路径共享同一知识并能降低真实分叉风险时才提取核心抽象。
- 算法代码优先使用算法表示分析：输入输出、数据结构、复杂度、终止性、边界和失败性质；不要用业务模型或数据库结构替代算法本身。
- 接口、编排和适配代码优先检查契约、表示映射、错误传播、资源生命周期和外部副作用；不把内部模型或存储结构未经验证地暴露到边界。
- 同一功能可以组合多个职责视角；视角用于选择证据、表示和验证方式，不自动决定目录结构、类层次或设计模式。需要状态分析时，按任务实际涉及的维度区分业务状态、数据表示/有效性状态、执行控制状态、持久化一致性状态、并发版本状态和外部副作用状态，避免把它们混为一个状态字段或状态机。

## 1. 从证据选择实现方式

### 1.1 生成前边界检查

新增入口、跨模块功能、数据表示变化、事务或外部副作用需要推导，或 Agent 将生成多个相互依赖的构件时，先形成与任务风险匹配的最小设计检查：目标与非目标、入口到输出路径、模块职责和数据所有权、表示转换、关键不变量、失败处理以及测试或观察接缝。该检查用于约束实现，不预设面向对象、分层、DDD、函数式或其他设计模式。

满足独立缺陷快速路径时不要求额外设计检查；但仍须明确预期行为、保持不变行为和验证方式。

- 先观察当前模块的语言惯例、组织方式、依赖方向、状态管理、错误处理、测试接缝和构建约束，再决定本次实现如何表达。
- 先确认当前修改点承担的数据、业务、算法或边界职责，再选择最贴合该职责的表示和验证接缝；跨职责代码只保留必要的显式转换，不混淆各自的不变量。
- 现有项目默认延续已验证且适用于当前问题的主导模式；只有该模式无法满足目标或会产生具体风险时，才选择不同方式并说明依据。
- 新项目或新边界没有既有模式时，自主选择最小充分结构；不默认要求类、接口、继承、分层、纯函数、切面、领域对象或其他特定构造。
- 用户负责目标、业务语义和工程边界；边界内的代码组织、数据表达、控制流和组合方式根据证据决定。存在多个同样可行的方向时，不因偏好的范式名称作选择。
- 比较候选实现时，记录新增概念/文件/类型、代码与依赖、共享状态、分支和调用跳转、与项目主导模式的偏差、需新增的测试接缝、定位失败所需观察点、影响边界和回退步骤；不只使用“清晰”“优雅”“容易维护”等未附证据的评价。
- 实现方式会改变公开契约、数据形态、安全边界、部署运维模型或主要技术方向时，返回 `./agent.md` 主流程并按 `./technology-selection.md` 处理。

## 2. 抽象与复用判断

- 先直接解决已确认的问题，再判断是否需要抽象；不得先设计通用框架再寻找用途。
- 重复次数只是调查信号，不是机械门槛。仅当重复表达相同知识、具有一致的变化原因，且提取后能降低真实维护或分叉风险时才合并。
- 引入公共模块、间接层、适配层、扩展点或可替换边界前，至少证明一项：已有多个真实使用方；已有不同实现；存在必须隔离的外部变化；测试或安全边界无法用更简单方式建立。
- 如果抽象新增的类型/模块、调用跳转、配置、约束和测试接缝，不少于它删除的重复规则、分叉路径或独立维护点，保留局部直接实现；无法比较时不因偏好抽象。
- 涉及金额、权限、安全或一致性规则时，优先防止同一规则多处独立演化；但仍应选择项目内最小、可验证的集中方式。

### 封装目标

封装优先用于隔离变化原因、外部依赖、状态不变量、权限、事务或资源生命周期。新增封装必须能说明被隔离的变化、状态或不变量，以及如何通过测试或契约验证边界；不为生成代码数量、目录对称或未来扩展增加层级。

## 3. 边界、依赖与状态

- 依据变化原因、业务不变量、生命周期、权限边界和失败处理划分职责，不依据范式模板强行拆分。
- 同一输入输出契约、状态生命周期或失败处理下共同变化的代码优先共址；具有不同消费者、发布节奏、权限边界或变化原因时再分离。
- 依赖稳定、必要且可验证的外部行为，避免读取其他模块无关的内部细节；长调用链妨碍定位或验证时收拢交互面。
- 隐式共享状态、执行顺序、依赖注入、缓存、重试或错误吞没会影响正确性时，将其变为可追踪、可测试的显式行为。
- 不为追求结构对称、目录整齐或模式完整而增加没有行为价值的文件、类型或层级。

## 4. 实现与修改纪律

- 修改前明确预期行为、保持不变的行为和验证方式；实现只覆盖本次目标所需范围。
- 命名、文件组织、错误表达和格式遵循当前语言及项目中可验证的主导风格，不套用其他语言的惯例。
- **保留文件编码**：修改代码文件时，必须保持原有 BOM 状态：文件开头已有 `EF BB BF` 时不得删除或转换，原本没有时不得新增；将该字节序列视为文件内容。
- 不顺手重构、重命名或格式化无关代码；若必要修复依赖邻近重构，说明因果关系并把范围控制在最小可验证边界。
- 注释只描述非显而易见的实现意图、边界或已落地的关键决策；不复制用户要求、规则、任务过程或未验证假设。
- 错误处理保留定位问题所需的原因和上下文，不静默忽略失败，也不泄露密钥、凭据或敏感数据。
- 性能优化以测量结果和目标约束为依据；没有证据时优先满足正确性、具有可追踪控制流和项目主导模式证据的实现。

## 5. 验证与自检

- 测试和检查优先验证可观察行为与稳定边界，不复制实现步骤来证明实现本身。
- 修复缺陷时覆盖能在修复前失败、修复后通过的最小回归场景，并检查相邻关键行为未退化。
- Agent 生成多个相互依赖的构件后，沿至少一条用户可观察路径复核入口、数据转换、关键不变量、失败处理、资源生命周期和输出；每个新增入口、类型、适配器、配置和转换都必须有当前消费者或明确验证用途。
- 测试应覆盖目标路径及关键失败边界，而不只覆盖生成的局部函数；未接线、无消费者或仅为未来扩展的构件不得保留。
- 性能、容量、延迟、吞吐或资源消耗是目标或方案依据时，先记录可重复基线和测量环境，再用相同工作负载比较；没有可比测量时不得声称优化完成。
- 完成前自检：是否引入未要求的功能；能否减少新增概念、文件/类型、依赖、配置、状态、分支或调用跳转而不损害成功标准；每个新增概念是否有当前消费者；依赖与状态能否从入口追到输出；是否匹配项目现实；验证是否覆盖用户成功标准。
- 若另一实现同样满足成功标准和项目约束，且新增概念、依赖、状态、分支、跳转、验证或回退步骤更少，应采用该实现。

## 6. 安全与日志边界

- 密钥、凭据和连接字符串不得硬编码、提交到版本库或写入日志。
- 日志只记录诊断所需的最少信息；敏感字段按项目规则脱敏，不无必要地关联个人标识、金额、权限或认证信息。
- 认证、授权、校验、事务、审计和异常处理放置在能够稳定执行并可验证的边界；具体实现方式由当前技术栈和项目结构决定，业务规则不得因基础设施机制而隐式改变。
