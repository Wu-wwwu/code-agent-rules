# 业务分析与决策

## 1. 业务流与数据流
分离记录，双向关联。业务流描述"做什么"，数据流描述"数据怎么变"。通过 `/documents/data-flow.md` 全局映射表关联。

## 2. 变更影响分析

| 场景 | 动作 |
|------|------|
| 新增/修改业务步骤 | 定位步骤 → 扫描关联数据流节点 → 评估 DB/API/测试影响 |
| 新增/修改数据流节点 | 定位节点 → 反向查业务步骤 → 确认用户可见影响 |
| 数据库表结构变更 | 找依赖节点 → 评估读写影响 → 确定迁移需求 |
| 外部 API 变更 | 契约对比 → 评估解析/降级 → 版本兼容 |

输出影响清单：受影响元素、类型、影响说明、优先级。

## 3. 决策框架

四步流程：识别冲突 → 比较所有真实可行路径及主要优缺点 → 推荐方案及理由 → 标注影响范围。通常至少比较两个候选；若证据表明只有一个可行路径，明确其他方向的排除依据，并把“维持现状 / 暂不实施”作为基线，不为满足数量要求编造伪方案。

选择依据是当前技术方案、数据结构和流程说明的辅助证据，不是逐次追加的任务日志。优先在相关说明旁保存一个主要位置，其他文档引用；只记录对未来修改有影响、无法从当前代码、契约或有效约定直接推导的理由。最小内容为：当前选择及适用范围、成立前提与证据、仍然有效的关键取舍、重新评估或失效条件。目标选择与已验证实现分开，不把方案确认当作实现事实。

### 记录内容与适用范围

- 项目说明只记录当前状态、当前约束、适用范围和可复核依据；不把用户原话、任务过程、修改日期、主观评价或未验证后果写成当前事实。
- 代码注释只保留非显而易见的当前意图、边界、不变量或已落地选择；日期、用户输入、确认过程、历史原因和普通决定不进入注释。运行日志只保留诊断、审计或运行观察所需的最少信息，并按安全规则脱敏。
- 决策记录只保留当前选择、适用范围、当前有效约束、证据和复核/失效条件。状态、编号、日期、替代关系或否决理由只有在生命周期、审计留存或当前约束识别确实需要时才保留；不为完整格式制造字段。
- 后果只记录已观察到的实际影响，或带明确条件、范围和证据的可验证影响；不得把推测、情绪判断或历史叙述写成事实。用户确认只说明目标、约束或授权，不证明实现正确，也不替代代码、配置、测试和运行证据。
- 记录内容应区分当前事实、当前约束、待验证推断和历史/审计材料；历史和审计材料仅作为待核实依据，不能覆盖当前直接证据或授权边界。

只有满足下述独立建档条件时才使用 `/documents/decision-log.md` 的“决策记录”区；记录当前选择、适用范围、当前说明引用、成立前提、证据和复核/失效条件，按需补充仍影响当前约束的替代关系或否决条件。编号、日期、状态（active / rejected / superseded）仅在需要识别生命周期、审计留存或当前依赖时记录；rejected 只保留仍可能影响当前判断的否决前提和重提条件，不保留无当前用途的过程叙述。破坏性变更的事实、授权和验证记录按 `destructive-analysis.md` 的“变更审计记录”区单独记录，不因审计记录自动创建决策。

### 新建决策条件

就地保存的选择依据不要求满足条件 1；只有以下条件全部满足，才新建独立决策记录：

1. **撤销需要协调**：撤销涉及数据恢复/重算、消费者迁移、停机/切流、跨环境同步或撤销外部副作用；
2. **不能从现有证据直接推导**：仅看代码、配置、测试、有效项目约定和主导模式，无法自然得出该选择；
3. **存在真实权衡**：至少两个可行方向在契约、数据、安全、部署运维、性能、维护或回退后果上不同。
4. **有未来复用价值且需统一引用**：跨模块或跨文档的长期取舍需要单一依据；缺失会导致误改仍有效约束、误判兼容边界或重复代价较高的调查，且相关当前说明无法就地充分承载。

任一不满足则不建独立档案；必要依据就地保存或仅在任务结果说明。只有一个可行路径时按需说明排除依据，不把伪候选当作真实权衡。

方案分析、候选比较、用户提出要求或用户确认执行，不单独构成需要记录的决策；不得为了创建决策记录而额外制造方案、确认或决策流程。

### 依据生命周期

- 当前变更涉及某项依据时才复核其适用范围、前提和依赖，不扫描全部历史。仍约束当前方案的依据保留在相关说明旁。
- 已替代但仍影响消费者兼容、迁移、回退或审计留存的，保留必要旧依据、替代关系和可观察移除条件；代码已修改不等于依赖已消失。
- 已替代或前提失效且无当前依赖的，退出当前说明和默认查询；仅在需要解释历史时定向读取归档或版本历史。查询价值与留存义务分别判断。
- 重复、临时或无复用价值的内容，在授权范围内合并或清理，并修复引用；确认没有兼容、迁移、回退和审计留存义务后才移除。依赖历史恢复前先确认有可定位的版本或归档，不假定未提交记录已保存；不改写版本历史，不顺带清理无关记录。

### 决策优先级

1. 数据安全/正确性 > 性能
2. 可维护性 > 代码简洁性
3. 显式 > 隐式
4. 内部一致性 > 外部最佳实践

## 4. 回查

1. 先读取当前动作涉及的方案、契约、数据或流程说明及关联依据，并核对当前实现证据。依据充分且无冲突时直接继续，不默认检索独立日志。
2. 仅当影响当前判断的依据缺失、证据冲突、拟改变仍有效的重要约束，或用户明确要求时定向追溯历史。按相关引用、任务描述中的用词、代码标识和已验证同义术语查索引、提交或归档，不扫描全部历史；档案缺失只表示覆盖不足，剩余未知不影响动作则继续。
3. 命中是待核实线索，不是自动约束。核对适用范围、成立前提和当前依赖；仅凭 active/rejected 状态或关键词不能判定仍有效。已失效且无当前依赖的记录不阻止当前方案；必要未知仍影响正确性或授权时先取证或请求确认，暂停依赖该结论的执行。
4. rejected 的否决前提仍成立且无新证据时，不重复同一无变化的提案；前提、需求或成本已变化，或重提条件满足时可重新评估，并说明证据。只有与当前有效授权、业务规则、外部契约或适用强制门禁冲突时，才暂停受影响执行并请求相应确认；历史记录本身不增加权限或构成永久否决。
5. 相关依据足以支持当前动作或已明确阻塞时退出；变更完成后按「依据生命周期」对齐受影响依据，避免方案说明和独立档案重复维护同一结论。

### 独立缺陷快速路径

以下局部缺陷条件可直接证明无需历史检索，但不是免检索的唯一情形；其他任务仍按「回查」中的实际触发判断：

1. 目标行为有直接、可验证的依据，例如既有契约、已有测试、对照实现或用户明确确认；当前偏差可通过失败测试、稳定复现或等价证据证明。存在多个对照实现且彼此矛盾时，视为无直接依据。
2. 修改局限于既有实现接缝，不需要在多个真实设计方案之间选择。
3. 不改变公开 API、Schema、数据格式、业务规则、权限、架构边界、共享配置或全局执行顺序。
4. 影响范围可由代码引用、调用关系和测试闭环，且没有证据表明缺陷与历史设计选择有关。

使用快速路径时，仅在任务结果中简要说明目标行为依据和修改边界，不因此建档。任一条件不满足不自动要求历史检索，先检查当前依据是否足够；影响分析、风险升级、测试、受影响文档对齐和完成验证仍然适用。

## 5. 破坏性影响分析（业务维度）

检查：规则冲突、目标冲突、流程冲突、语义冲突、权限冲突。

> 完整破坏性分析（分级、预测、标记、累积升级）以 `./destructive-analysis.md` 为准。

## 6. 业务规则分析

涉及状态、金额、权限、角色或其他业务决策时：
1. 定位并引用 `/documents/business-rules.md` 中的对应规则条目；没有可验证依据时，不得推测目标行为。
2. 识别时间、状态、金额、角色等边界条件，选取最多 3 个与当前改动直接相关的关键场景请求确认。
3. 使用伪代码或流程图明确前置条件、全部判断分支和返回结果。
4. 实现时在关键判断处标注对应业务规则编号；规则缺失、冲突或边界不明确且影响正确性时暂停。
