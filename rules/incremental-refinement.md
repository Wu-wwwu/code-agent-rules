# 增量细化与归并原则

## 问题识别

Agent 在多轮对话中倾向于**累加式生成**而非**归并式细化**，导致：
- 用户每次补充需求，Agent 生成新代码而不归并到已有实现
- 同一业务概念在代码、模型、文档中重复表达但细节不一致
- 大量条件分支实际判断相同前提，但分散在多处
- 文档记录逐轮追加用户意见，而非收敛到统一的当前状态

**根本原因**：当前规则的"最小改动"只约束了单次修改的范围，未约束多轮理解的归并方式。

---

## 核心原则

### 1. 需求理解的归并式细化

用户多轮补充时，不是在已有理解后**追加新条目**，而是**细化已有条目的边界和约束**。

#### 反模式（累加式）

```
第1轮：用户要订单管理
  → Agent 理解为"创建订单、查询订单"

第2轮：用户补充"订单可以取消"
  → Agent 追加"取消订单"功能

第3轮：用户说"已支付的不能取消"
  → Agent 追加"支付状态检查"

最终：3 个独立功能 + 1 个检查，分散实现
```

#### 正确模式（归并式细化）

```
第1轮：用户要订单管理
  → Agent 理解为"订单生命周期管理"
  → 边界未知：状态转换、允许操作、约束条件

第2轮：用户补充"订单可以取消"
  → 细化状态转换：created/paid/cancelled
  → 细化允许操作：create/pay/cancel
  → 约束条件仍未知

第3轮：用户说"已支付的不能取消"
  → 细化约束：cancel 仅允许在 created 状态
  → 归并为单一状态机模型

最终：1 个订单状态机，边界清晰
```

#### 操作要求

1. **识别归并信号**：新输入是"新的独立需求"还是"已有需求的边界细化"？
   - 涉及相同数据实体 → 归并
   - 约束/否定已有行为 → 细化边界
   - 补充分支/异常 → 细化已有路径
   - 全新领域/独立目标 → 新增

2. **归并前还原当前理解**：
   - 已确认：哪些行为、状态、约束
   - 已排除：哪些情况明确不在范围
   - 未知边界：哪些条件尚未明确

3. **细化方式**：
   - 边界收窄：原本"所有订单可取消" → "仅未支付订单可取消"
   - 分支补全：原本"成功路径" → "成功 + 3 种失败"
   - 约束显式化：原本"能操作" → "能操作 when 条件 C"

4. **归并后验证一致性**：
   - 新约束是否与已有约束冲突？
   - 细化后的边界是否仍覆盖第 1 轮确认的核心目标？
   - 是否产生了无法到达的状态或死锁？

### 2. 代码实现的归并而非累加

#### 反模式（累加式代码）

```python
# 第 1 轮
def create_order(user_id, items):
    order = Order(user_id=user_id, items=items)
    db.save(order)
    return order

# 第 2 轮：补充"可以取消"
def cancel_order(order_id):
    order = db.get(order_id)
    order.status = 'cancelled'
    db.save(order)

# 第 3 轮：补充"已支付不能取消"
def cancel_order(order_id):
    order = db.get(order_id)
    if order.status == 'paid':  # 新增检查
        raise Exception("不能取消已支付订单")
    order.status = 'cancelled'
    db.save(order)

# 问题：
# - create_order 未设置初始状态
# - 状态转换分散在各个函数
# - 没有统一的状态验证
```

#### 正确模式（归并式代码）

```python
# 第 1 轮：识别这是状态管理
class Order:
    STATES = ['created', 'paid', 'cancelled']
    
    def __init__(self, user_id, items):
        self.user_id = user_id
        self.items = items
        self.status = 'created'  # 显式初始状态

# 第 2 轮：归并"可以取消"到状态转换
class Order:
    STATES = ['created', 'paid', 'cancelled']
    TRANSITIONS = {
        'created': ['paid', 'cancelled'],  # 边界待细化
        'paid': ['cancelled'],             # 边界待细化
        'cancelled': []
    }
    
    def cancel(self):
        if 'cancelled' not in self.TRANSITIONS[self.status]:
            raise InvalidTransition(f"Cannot cancel from {self.status}")
        self.status = 'cancelled'

# 第 3 轮：细化转换约束（不是新增代码，是修改约束）
class Order:
    TRANSITIONS = {
        'created': ['paid', 'cancelled'],
        'paid': [],  # 细化：已支付不能取消
        'cancelled': []
    }
    # cancel() 方法无需修改，约束已归并到 TRANSITIONS
```

#### 操作要求

1. **改动前识别归并机会**：
   - 新功能与已有函数操作相同数据 → 归并到已有模块
   - 新约束限制已有行为 → 归并到已有验证逻辑
   - 新分支补充已有流程 → 归并到已有状态机/控制流

2. **归并方式**：
   - **状态显式化**：分散的布尔标志 → 统一状态枚举
   - **约束集中化**：重复的 if 判断 → 统一验证函数/配置
   - **转换统一化**：分散的状态改变 → 统一转换接口

3. **禁止行为**：
   - 为新需求复制已有函数并修改部分逻辑
   - 在已有函数外层再包装一层检查
   - 新增平行的相似函数（除非确实是不同业务概念）

### 3. 文档记录的收敛而非追加

#### 反模式（追加式文档）

```markdown
## 订单管理功能

### 2026-10-01 初始需求
- 用户要求：创建订单、查询订单
- 实现：Order 实体，POST /orders, GET /orders/:id

### 2026-10-05 补充需求
- 用户要求：订单可以取消
- 实现：新增 cancel_order 函数，PATCH /orders/:id/cancel

### 2026-10-08 约束细化
- 用户要求：已支付的不能取消
- 实现：在 cancel_order 中增加状态检查

## 问题
- 3 次追加，每次都是"用户要求 → 实现"
- 无法从文档看出当前完整的订单行为边界
- 决策依据分散在 3 个时间点
```

#### 正确模式（收敛式文档）

```markdown
## 订单状态管理

**当前状态**：订单生命周期由状态机管理，支持创建、支付、取消操作。

**状态定义**：created | paid | cancelled

**允许转换**：
- created → paid：用户完成支付
- created → cancelled：用户取消订单（仅未支付可取消，证据：2026-10-08 用户确认）
- paid → (无转换)：已支付订单不可取消

**操作接口**：
- POST /orders：创建订单，初始状态 created
- PATCH /orders/:id/pay：支付订单，转换为 paid
- PATCH /orders/:id/cancel：取消订单，仅在 created 状态允许

**实现位置**：Order.cancel() @ src/orders/model.py:42

**细化历史**（仅保留影响当前约束的关键决策）：
- 2026-10-08：已支付订单不可取消（用户确认，业务规则）
```

#### 操作要求

1. **每轮更新时重写受影响章节**，而非追加新段落：
   - 用"当前状态、目标状态、差异"结构
   - 合并重复描述
   - 删除已被细化覆盖的模糊描述

2. **决策依据只保留一个权威条目**（已在 business-analysis.md:43）：
   - 同一决策被多次细化时，合并为最新有效表述
   - 保留影响当前约束的关键前提和证据
   - 删除已被覆盖的中间推测

3. **历史细化过程不作为默认字段**：
   - 不记录"第 1 轮→第 2 轮→第 3 轮"
   - 不记录"用户说 X→讨论后决定 Y"
   - 只有影响审计、回退、有效期判断时才保留时间戳和来源

## 4. 概念模型的去重与归并

#### 问题：同一业务概念的多重表达

```
代码中：Order, OrderEntity, OrderDTO, OrderRequest
数据库：orders 表
文档中：订单、Order、订单实体
API：/orders 路径

实际上都是同一个业务概念，但：
- 6 种名称
- 字段不完全一致（DTO 缺少内部字段，Request 多了验证）
- 文档中对"订单"的描述散落 3 处，互相冲突
```

#### 归并原则

1. **识别同一概念的多重表达**：
   - 有显式映射、ORM 配置、序列化关系 → 同一概念的不同表示
   - 字段大部分重叠 + 生命周期相同 → 同一概念
   - 仅凭名称相似 → 不足以判断，需要证据

2. **归并到 glossary.md**：
   ```markdown
   ## 订单 (Order)
   
   **业务概念**：用户购买商品的交易记录
   
   **表示形式**：
   - 代码：Order (src/orders/model.py)
   - 数据库：orders 表
   - API 输入：OrderRequest (DTO，仅包含用户可见字段)
   - API 输出：OrderDTO (DTO，排除内部状态)
   
   **核心字段**：id, user_id, items, status, created_at
   
   **映射证据**：
   - Order → orders：SQLAlchemy ORM @ src/orders/model.py:8
   - Order → OrderDTO：to_dto() @ src/orders/model.py:67
   ```

3. **代码中消除重复判断**：
   - 同一前提在多处判断 → 提取为 Order.can_cancel()
   - 同一数据转换在多处实现 → 提取为 Order.to_dto()
   - 同一验证逻辑在多处重复 → 提取为 Order.validate()

## 5. 触发归并的信号

Agent 在以下情况必须先尝试归并，而非直接累加：

1. **新输入涉及已有实体的行为边界**：
   - "订单可以取消" → 归并到订单状态管理
   - "管理员可以强制取消" → 归并到订单权限模型

2. **新约束否定或限制已有行为**：
   - "已支付的不能取消" → 细化状态转换约束
   - "单笔订单不超过 100 件商品" → 归并到订单验证规则

3. **新分支补充已有流程**：
   - "支付失败时记录原因" → 归并到支付流程的失败处理分支
   - "库存不足时降级到预订" → 归并到库存检查的分支

4. **发现重复表达**：
   - 2 个函数包含相同的 5 行判断逻辑
   - 3 处文档描述同一业务规则但措辞不同
   - 代码、模型、文档对同一实体的字段定义不一致

5. **用户用"也"、"另外"、"补充"等词**：
   - 语义上表明是对已有内容的扩展，而非全新需求

## 6. 归并操作的验证

归并后必须验证：

1. **原有能力未丢失**：
   - 第 1 轮确认的核心行为仍然可达
   - 已有测试仍然通过

2. **新约束已生效**：
   - 细化后的边界能阻止不允许的操作
   - 补充的分支能被测试覆盖

3. **不存在冲突**：
   - 新约束与旧约束不矛盾
   - 状态转换不产生死锁

4. **概念一致性**：
   - 代码、模型、文档对同一实体的描述一致
   - 字段映射、类型、约束对齐

## 8. 评测案例设计

**Case Q: 多轮需求归并**

场景：
1. 用户："实现用户注册功能"
2. Agent 实现基础注册（用户名、密码）
3. 用户："邮箱要验证才能激活"
4. Agent 补充邮箱验证逻辑
5. 用户："用户名不能重复"
6. Agent 补充唯一性检查

预期：
- Agent 不生成 3 个独立函数（register, verify_email, check_duplicate）
- 而是归并为 1 个用户注册状态机：pending → email_verified → active
- 唯一性检查归并到注册前验证，而非独立函数
- 文档最终只有 1 个"用户注册流程"章节，而非 3 次追加
