# 数据结构分析

## 概念边界

- **代码构件**：类、结构体、接口、DTO、消息、变量、函数参数、Schema、表、文档结构等具体表示。
- **数据实体**：为追踪同一组数据而建立的中性分析概念，可关联多个代码、传输和存储表示；它不是必须新增到代码中的领域对象。
- **现实语义对象**：现实领域知识和概念。

代码构件的名称只提供检索线索。除非用户说明、有效业务资料、代码行为、Schema 约束或测试明确证明，数据实体不得自动等同于同名现实对象，也不得依据行业常识补全字段、关系、约束、生命周期或业务规则。现实语义与当前编码任务无关时，使用中性名称并仅保留数据处理所需含义。

## 实体识别与归并

1. 从类型定义、字段、参数、返回值、Schema、数据库表、序列化格式、查询和测试中提取候选代码构件。
2. 记录每个候选的标识、字段、键、约束、来源位置及进入/离开系统的方式；名称相似不能单独证明是同一实体。
3. 只有存在显式映射、字段对应、ORM/序列化配置、Schema 引用、转换函数、调用链、查询或测试证据时，才把多个表示归并到同一数据实体。
4. 为需要跨表示追踪的实体分配稳定中性标识（如 `DE-001`），分别记录代码表示、传输表示和存储表示；证据不足时保留为独立候选并标记待确认。

## 关系建模

现有项目先按可定位证据建立关系，不凭对象名称或现实常识推断。可用证据包括：

- 类型引用、字段包含、继承或组合；
- 主键、外键、唯一约束、关联表和查询 JOIN；
- Schema `$ref`、ORM/序列化映射和消息契约；
- 函数输入输出、调用链、显式转换和测试断言；
- 用户确认或有来源的有效项目资料。

关系边必须记录“来源构件—关系类型—目标构件—证据位置”。1:1、1:N、N:M 是已证实关系的实现候选，不是仅凭业务名称得出的默认结论。设计新关系时，业务目标尚未确认则标记待确认，不用外部领域知识替代证据。

## 构件创建与变换

按实际存在的流程追踪同一数据实体的表示变化：

`来源/创建 → 校验 → 读取/补全 → 变换 → 持久化/传递 → 输出`

每一步记录输入表示、执行构件、输出表示、字段映射、增删/重命名/格式变化、约束变化及证据。不要把名称相同视为“未发生变换”，也不要把名称不同视为“必然是不同实体”。详细链路按 `./data-flow-methodology.md` 输出。

### 内存变换与持久化处理

- **内存变换**：进程内数据在类型、字段、约束、可变性、生命周期、复制/共享和计算结构上的变化；重点验证输入输出、不变量、边界、异常和复杂度。
- **持久化处理**：数据跨越存储边界的读取、写入、提交、可见性、事务、锁、幂等、恢复、迁移和索引行为；重点验证存储约束、并发、失败恢复和数据完整性。
- 两者之间的序列化、映射、批处理、缓存或异步队列属于边界处理，不能默认归入任一侧；按实际数据流和可观察后果单独验证。

### 状态维度

需要分析状态时，至少区分适用的维度：业务状态、数据表示/有效性状态、执行控制状态、持久化一致性状态、并发版本状态和外部副作用状态。相同字段或枚举只有在证据证明它们生命周期和不变量相同，才能合并为一个状态；否则保持独立并追踪转换关系。

## 字段推导
查询条件、结果显示、关联键字段，标注来源（输入、原表、聚合计算、关联查询、外部 API）和经过的变换。无法从代码或有效资料验证的现实含义标记为未知，不依据字段名称自行解释。

## 冗余权衡

规范化、冗余、宽表和 JSON 都是候选表示，不根据字段数量、记录条数或读写频率单独决定。比较候选时至少检查权威来源、一致性窗口、更新传播、失败修复、查询形状、索引、序列化与存储成本、历史数据回填、迁移成本以及权限和审计要求。

冗余字段只有在权威来源、同步机制、失败处理、过期处理和修复路径明确时才可采用。JSON 或其他非结构化表示不得承载需要强约束、频繁过滤、排序、聚合、唯一性校验或权限判断的核心字段，除非已有产品语义和测量证据支持。

## 索引策略

索引必须从实际查询、数据分布和数据库产品语义推导，不从字段名称或通用顺序机械生成。对候选索引检查 WHERE、JOIN、ORDER BY、GROUP BY、分页方式、联合索引列顺序、选择性和数据分布、覆盖列、写入和维护成本、锁与执行计划，以及是否存在重复或相互覆盖的索引。

外键约束、外键列索引和级联删除是不同决策，不能合并处理。是否为外键列建立索引，依据实际连接、删除或更新父记录、查询形状、数据量和执行计划判断。低选择性列不得仅凭经验排除，应检查其在联合索引、分区、数据倾斜或实际查询中的作用。只有数据库产品明确支持时，才使用 INCLUDE、聚簇、部分索引、函数索引或其他专属特性。

## 表示选择的证据要求

主键、外部标识、文件内容、JSON、结构化列、批处理和缓存策略均为候选设计，不得仅凭通用经验自动固定。选择主键或标识时检查唯一性生成范围、单库或多库写入、离线生成、对外暴露、索引和关联存储成本、插入顺序、数据库原生支持、序列化兼容以及迁移与回退成本。

选择数据库、文件系统或对象存储时检查内容大小和数量分布、访问频率、事务一致性、备份恢复、CDN、范围读取、版本管理、日志复制和缓存压力、权限与生命周期、失败后的孤儿对象或元数据，以及成本和运维边界。固定大小阈值只能作为当前环境的待验证假设，必须注明数据库、运行时、存储产品、负载和测量条件，不得写成跨产品通用门槛。

## 性能、容量与写入策略

性能和容量结论必须由目标与测量驱动，不只由记录条数或经验阈值决定：

1. 明确成功指标：延迟、吞吐、峰值内存、数据库负载、锁等待、成本、失败率或维护窗口；没有目标时不得把“更快”当作已证实需求。
2. 记录工作负载：数据量与分布、并发度、事务边界、网络往返、索引与约束、是否需要返回生成值、幂等与失败恢复要求。
3. 建立可重复基线：固定环境、版本、输入和测量方法；优先基准、剖析、查询计划或生产遥测，不用单次主观观察下结论。
4. 选择最小充分策略：逐条、批量 API、数据库原生导入、流水线或分片都只是候选；以项目实测、数据库官方约束和兼容边界决定。
5. 验证最坏路径与正确性：检查事务时长、锁、日志/复制压力、内存、超时、部分失败、重试与回退；性能提升不得牺牲数据一致性和可恢复性。

没有项目数据时可用小规模试验或官方建议形成待验证假设，但不得把固定数量阈值写成通用门槛。非关系型存储按对应产品语义和实测决定。
