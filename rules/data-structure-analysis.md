# 数据结构分析

## 概念边界

- **代码构件**：类、结构体、接口、DTO、消息、变量、函数参数、Schema、表、文档结构等具体表示。
- **数据实体**：为追踪同一组数据而建立的中性分析概念，可关联多个代码、传输和存储表示；它不是必须新增到代码中的领域对象。
- **现实语义对象**：商业订单、付款、建筑元素、工业元素、自然资源等现实概念。

代码构件的名称只提供检索线索。除非用户说明、有效业务资料、代码行为、Schema 约束或测试明确证明，数据实体不得自动等同于同名现实对象，也不得依据行业常识补全字段、关系、约束、生命周期或业务规则。现实语义与当前编码任务无关时，使用中性名称并仅保留数据处理所需含义。

## 实体识别与归并

1. 从类型定义、字段、参数、返回值、Schema、数据库表、序列化格式、查询和测试中提取候选代码构件。
2. 记录每个候选的标识、字段、键、约束、来源位置及进入/离开系统的方式；名称相似不能单独证明是同一实体。
3. 只有存在显式映射、字段对应、ORM/序列化配置、Schema 引用、转换函数、调用链、查询或测试证据时，才把多个表示归并到同一数据实体。
4. 为需要跨表示追踪的实体分配稳定中性标识（如 `DE-001`），分别记录代码表示、传输表示和存储表示；证据不足时保留为独立候选并标记待确认。

## 关系建模

现有项目先按可定位证据建立关系，不凭对象名称或现实常识推断。可用证据包括：

- 类型引用、字段包含、继承或组合；
- 主键、外键、唯一约束、关联表和查询 JOIN；
- Schema `$ref`、ORM/序列化映射和消息契约；
- 函数输入输出、调用链、显式转换和测试断言；
- 用户确认或有来源的有效项目资料。

关系边必须记录“来源构件—关系类型—目标构件—证据位置”。1:1、1:N、N:M 是已证实关系的实现候选，不是仅凭业务名称得出的默认结论。设计新关系时，业务目标尚未确认则标记待确认，不用外部领域知识替代证据。

## 构件创建与变换

按实际存在的流程追踪同一数据实体的表示变化：

`来源/创建 → 校验 → 读取/补全 → 变换 → 持久化/传递 → 输出`

每一步记录输入表示、执行构件、输出表示、字段映射、增删/重命名/格式变化、约束变化及证据。不要把名称相同视为“未发生变换”，也不要把名称不同视为“必然是不同实体”。详细链路按 `/rules/data-flow-methodology.md` 输出。

## 字段推导
查询条件、结果显示、关联键字段，标注来源（输入、原表、聚合计算、关联查询、外部 API）和经过的变换。无法从代码或有效资料验证的现实含义标记为未知，不依据字段名称自行解释。

## 冗余权衡
- 查询频繁 + 字段 ≤3 + 更新频率低 → 允许冗余
- 一致性要求高或更新频率高 → 必须规范化

## 索引策略
从查询推导：WHERE 等值 → 范围 → JOIN（外键必建）→ ORDER BY → INCLUDE。低选择性字段不单独建索引。

## 性能、容量与写入策略

性能和容量结论必须由目标与测量驱动，不只由记录条数或经验阈值决定：

1. 明确成功指标：延迟、吞吐、峰值内存、数据库负载、锁等待、成本、失败率或维护窗口；没有目标时不得把“更快”当作已证实需求。
2. 记录工作负载：数据量与分布、并发度、事务边界、网络往返、索引与约束、是否需要返回生成值、幂等与失败恢复要求。
3. 建立可重复基线：固定环境、版本、输入和测量方法；优先基准、剖析、查询计划或生产遥测，不用单次主观观察下结论。
4. 选择最小充分策略：逐条、批量 API、数据库原生导入、流水线或分片都只是候选；以项目实测、数据库官方约束和兼容边界决定。
5. 验证最坏路径与正确性：检查事务时长、锁、日志/复制压力、内存、超时、部分失败、重试与回退；性能提升不得牺牲数据一致性和可恢复性。

没有项目数据时可用小规模试验或官方建议形成待验证假设，但不得把固定数量阈值写成通用门槛。非关系型存储按对应产品语义和实测决定。
