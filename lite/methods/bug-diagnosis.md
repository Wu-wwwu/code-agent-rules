# Bug 诊断方法

> **触发**：竞态/时序/非确定/跨模块 Bug 或无法稳定复现；**快速路径**：有直接可验证依据、改动限于既有接缝且不碰公开 API/Schema/数据格式/业务规则/权限/架构时直接修复验证。

## 快速路径判定（全部满足则跳过诊断流程）

- 目标行为有直接依据（既有契约、已有测试、用户明确确认）
- 当前偏差可通过失败测试、稳定复现或等价证据证明
- 修改局限于既有实现接缝，不需多方案选择
- 不改变公开 API、Schema、数据格式、业务规则、权限、架构边界

## 完整诊断流程

### 阶段一：建立反馈回路

优先失败测试、HTTP 脚本、CLI 快照、请求回放、最小 harness。回路须秒级、断言精确、环境固定。

- 症状只在特定版本区间：版本二分定位引入点
- 时序窗口型竞态：循环触发脚本拉高命中次数
- 非确定性 Bug：先提高复现率并记录基线

### 阶段二：复现 + 最小化

确认症状一致，逐项删减至最小承重集合。

### 阶段三：假设

3–5 个可证伪假设，格式："若 X 是原因，则改变 Y 应使 Bug 消失 / 改变 Z 加重"。

### 阶段四：插桩

每探针对应一预测，一次改一变量。调试器优先，日志前缀 `[DEBUG-xxxx]`。

### 阶段五：修复 + 回归

最小复现 → 回归测试 → 看红 → 修复 → 看绿 → 重跑原始回路。

### 阶段六：清理

- 原始场景不复现；回归测试通过
- 调试日志删除；临时 harness 清理
- 架构性发现记入决策记录

**核心纪律：没有反馈回路，不许假设。造不出回路就停下，索要可复现环境或数据。**

## 日志规范

```
[DEBUG-0001] 假设H1：连接池耗尽
[DEBUG-0001] 预测：增加连接池大小应减少错误
[DEBUG-0001] 实际：错误未减少，排除H1
```
